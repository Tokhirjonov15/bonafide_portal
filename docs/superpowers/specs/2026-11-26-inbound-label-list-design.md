# 스캔 입고 라벨 일괄 출력 — 설계 (짧은 설계)

대상: `public/jaego/index.html` 만 수정 (서버·DB 변경 없음)

## 목적 (왜)
입고할 때마다 라벨을 뽑으면 잘못 입력한 것까지 인쇄되기 쉽다. 입고를 모두 끝내고 수량을 한 번 더 확인한 뒤,
맨 아래 [출력] 버튼으로 **한꺼번에, 확인 팝업을 거쳐** 라벨을 출력한다.

## 사용 상황 (사용자가 말한 것)
- 스캔 화면의 스캐너·카메라 입고는 관리자 외 직원이 입/출고에 쓴다 → **이 흐름이 대상**.
- 재고 현황의 + 버튼 입고는 관리자가 재고 수량을 맞출 때만 쓴다 → **대상 아님**(목록에 넣지 않음).
- 입고는 스캐너로 하므로 **새로고침해도 목록이 사라지면 안 된다.**

## 목표 / 비목표
- 목표: ① 스캔 화면에 "이번 입고 목록(미출력)"과 [라벨 출력] 버튼 ② 누르면 입고 품목 목록 팝업 + "출력하시겠습니까?" + 확인/취소
  ③ 확인 시에만 라벨 출력 화면으로 이동 ④ 새로고침·재접속해도 목록 유지 ⑤ 입고를 취소(되돌리기)하면 목록에서도 빠짐
- 비목표: 서버/DB 변경, + 버튼 입고의 라벨 흐름, 여러 PC 간 "출력 완료" 공유, 기존 [오늘 품목 라벨]·수정창 [라벨 인쇄] 제거(그대로 둠)
- 안티골: 입고할 때 라벨이 저절로 나오거나, 취소한 입고가 라벨로 나오는 것

## 접근 방법 (고른 것)
| 방법 | 장점 | 단점 |
|---|---|---|
| 1. 이 PC에 목록 저장(localStorage) | 가장 단순 | 입고 취소가 목록에 반영 안 됨, 브라우저 데이터 삭제 시 사라짐 |
| **2. 서버 입고 기록에서 계산 (선택)** | 서버 변경 없음, 새로고침 유지, 취소 자동 반영 | "어디까지 출력했는지" 표시만 PC에 저장, 최근 300건 한계 |
| 3. 서버에 출력 완료 표시 추가 | 여러 PC 정확 공유 | `src/index.js`·DB 열 추가 필요 (범위 밖) |

사용자가 2번을 선택했다.

## 설계
**목록 = `MOVEMENTS`(서버 `/state`의 최근 기록)에서 아래 조건을 모두 만족하는 입고 기록을 품목별로 합산**
- `type==="in"` 이고 메모가 `스캔 입고`로 시작 (스캔 화면 입고만 — + 버튼 입고는 메모가 달라 제외)
- `who === ME.id` (본인이 입고한 것)
- `ts >` 출력 기준 시각 (아래)
- 취소된 기록 제외 (기존 `취소:<id>` 메모 규칙 재사용), 취소 기록 자체도 제외

**출력 기준 시각**: `localStorage` 키 `jaego_lbl_mark_<ME.id>`. 값이 없으면 "오늘 0시".
[확인] 후 출력 화면이 열리면 포함된 기록의 가장 늦은 `ts`로 갱신 → 목록이 비워진다.
직전 값도 저장해 두고 **[방금 출력 취소·다시 불러오기]** 링크로 되돌릴 수 있게 한다(팝업 차단 등으로 못 뽑은 경우 대비).

**화면 (스캔 화면, "최근 스캔" 아래)**
```
이번 입고 목록 (미출력)
 거즈 4x4      입고 3박스    장수 [3]
 주사기 3cc    입고 1박스    장수 [1]
            [ 라벨 출력 (2품목 · 4장) ]
```
- 목록이 비면 영역과 버튼을 숨기거나 "출력할 입고가 없습니다"로 표시.
- 스캔 입고가 성공할 때마다 목록 갱신(기존 `refresh(true)` 뒤 렌더).

**라벨 장수 (내 판단 — 틀리면 고쳐 주세요)**: 기본값 = 입고한 **박스 수**(박스 크기 있는 품목은 `qty / boxSize`, 없으면 입고 수량). 목록의 `장수` 칸에서 고칠 수 있고 0이면 그 품목은 출력 안 함.

**확인 팝업**: 제목 "출력하시겠습니까?", 품목명·입고 수량·장수 목록, [취소] [확인]. [확인]만 출력 화면을 연다.
기존 팝업(`.ovl`/`.modal`) 스타일 재사용.

**출력 화면 연결**: 기존 `printBarLabels(items)`를 재사용한다. 이 목록에서 부르면 `items`에 `copies`를 담아 보내고,
그 경우 인쇄 창은 장수 입력칸(PR #1에서 추가) 대신 "총 N장"만 보여준다. `copies`가 없는 기존 호출([오늘 품목 라벨] 등)은 PR #1 동작 그대로.

**바코드 없는 품목**: 스캔으로 입고된 품목은 바코드가 있으므로 별도 처리 불필요.

## 제약
- Windows/Chrome, 라벨 프린터 BY-482BT, 서버는 Cloudflare Worker (이번엔 미변경)
- `MOVEMENTS`는 서버가 최근 300건만 준다 → 출력 안 한 입고가 300건 이상 쌓이면 오래된 것은 목록에서 빠진다(입고 직후 작업에서는 문제없음)
- 출력 기준 시각은 PC·계정별 저장 → 다른 PC에서는 같은 입고가 다시 "미출력"으로 보일 수 있다(비목표로 명시)

## 브랜치 / 병합 순서
`feature/inbound-label-list`는 PR #1(`feature/label-copies`) 위에 쌓는다. PR #1이 `develop`에 병합되면 이 브랜치를 `develop`으로 PR한다.
(PR #1보다 먼저 올려야 하면 base를 `feature/label-copies`로 해서 올리고, #1 병합 후 `develop`으로 바꾼다.)

## 확인 방법
localhost 정적 서버는 `/api`가 없어 `MOVEMENTS`를 흉내 내야 한다 → 콘솔에서 `MOVEMENTS`/`ME`를 임의로 채우고 목록 렌더 함수를 호출해 ①조건별 걸러짐(+버튼 입고·타인·취소·출력 이후) ②확인/취소 동작 ③새로고침 후 유지를 확인한다. 실제 입고·프린터 출력은 배포 후 확인.
