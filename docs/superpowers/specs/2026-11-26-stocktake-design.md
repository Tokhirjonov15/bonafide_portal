# 재고 실사(Stocktake) — 설계

대상: `public/jaego/index.html`, `src/index.js`, 새 모듈 `src/stocktake.js` (서버 변경 있음 — 새 표 2개, 새 경로 여러 개)

## 목적 (왜)
지금은 전산 재고와 실제가 다르면 관리자가 층별 수량을 직접 고친다. 그러면 **얼마나 틀렸는지·누가 언제 셌는지가 남지 않고**, 재고를 세는 일은 관리자 혼자 하게 된다.
재고 실사는 "직원이 실제 수량을 세어 넣는다 → 전산과의 차이를 모아 본다 → 관리자가 확정하면 그때만 재고가 바뀐다"는 흐름이다.
박스히어로(재고 조사), NetSuite(승인된 실사만 조정 반영), Cin7(창고별 실사)이 같은 방식이다.

## 목표 / 비목표 / 안티골
- **목표**: ① 층(+약품/물품)을 정해 실사를 시작 ② 직원이 품목을 스캔하거나 골라 실제 수량 입력(박스/개수) ③ 진행 현황(센 것/아직) ④ 차이 검토 화면 ⑤ 관리자가 확정하면 **차이만큼 조정 기록**을 남김 ⑥ 실사 내역을 나중에 다시 볼 수 있음
- **비목표**: 실사 중 입출고 막기(막지 않는다) · 로트(유통기한 묶음)별로 세기 · 일련번호 · 다단계 승인 · 정기 실사 일정/자동 알림 · 오프라인 입력
- **안티골**: 확정 전에 재고가 바뀌는 것 · 같은 실사를 두 번 확정해 조정이 두 번 들어가는 것 · 세는 동안 일어난 입출고가 조정에 섞여 재고가 틀어지는 것 · 안 센 품목이 저절로 0이 되는 것

## 제약
- 재고 수량은 저장하지 않고 입출고 기록(movements)의 합이다 → 실사 결과도 **기록으로만** 반영(수량 열을 바꾸지 않음). 되돌리기는 기존 [기록 → 취소]를 그대로 쓴다.
- 층별 재고 계산은 기존 방식(기록의 층, 비어 있으면 품목 위치의 층)을 그대로 쓴다.
- 대체 품목은 자기 재고를 가진 별개 품목이므로 실사 줄도 따로 둔다.
- 기존 기능은 지우지 않고, 층별 수량 직접 수정은 그대로 둔다.
- 서버는 Cloudflare Worker + D1, 화면은 `index.html` 한 파일 — 기존 방식 유지. 새 로직은 순수 함수 모듈로 빼서 `node --test`로 검증.

## 접근 방법
| 방법 | 장점 | 단점 |
|---|---|---|
| A. 화면에서만 계산하고 저장 안 함 | 서버 변경 없음 | 여러 직원이 나눠 못 세고, 새로고침·기기 변경에 날아감 |
| **B. 실사 세션을 서버에 저장 (선택)** | 여러 직원·기기가 같은 실사에 입력, 새로고침 유지, 내역 보존 | 표 2개·경로 추가 |
| C. 입출고 기록에 "실사" 종류만 추가 | 가장 단순 | 진행 현황·차이 검토·확정 개념이 없음 |

B로 간다. (이유: 입고 목록 때와 같이 "여러 직원이 스캐너로 나눠서 하고, 중간에 새로고침해도 남아야 한다"가 핵심이다. 제 판단이며 근거는 사용자가 말한 사용 방식이다.)

## 설계

### 데이터 (새 표 2개)
- `counts`: `id, name, floor, kind, status('open'|'done'|'cancelled'), blind(0/1), created_by, created_at, finished_by, finished_at, note`
- `count_lines`: `count_id, pid, counted, sys_at_count, counted_by, counted_at` — 기본키 `(count_id, pid)`
  - **`sys_at_count`는 서버가 센 순간 계산**한다(그 층의 그 품목 재고). 화면 값을 믿지 않는다.

### 핵심 계산 — 세는 동안의 입출고가 섞이지 않게
품목 줄의 조정량 = `counted − sys_at_count`.
이유: 센 뒤에 생긴 입출고는 이미 현재 재고에 반영돼 있고 실제 수량에도 똑같이 반영됐을 것이므로, 센 시점 기준 차이만 조정하면 현재 재고가 맞게 된다. 다시 세면 그 줄만 최신 값으로 덮어쓴다.

### 흐름
1. **시작**(관리자·직원 모두): 층 선택(3층/4층/10층), 구분(전체/약품/물품), 이름(기본 "11/26 3층 실사"). 같은 층·구분의 열린 실사가 있으면 새로 만들지 않고 그걸 이어서 연다.
2. **세기**(스캔 화면 방식 재사용): 바코드 스캔 또는 품목 선택 → 박스/개수 + 수량 입력(박스 크기 있으면 박스 기본). **0도 입력 가능**(없음 확인). 같은 품목을 다시 넣으면 덮어쓰고 "누가 언제"를 보여 준다. 기본은 **전산 수량 숨김(블라인드)** — 보고 맞추는 것을 막는다(시작할 때 끌 수 있음).
3. **진행 현황**: "센 품목 n / 대상 N", 아직 안 센 품목 목록(대상 = 그 층에 재고가 있거나 위치가 그 층인 품목).
4. **차이 검토**(관리자): 센 품목마다 전산·실사·차이·차이 금액(입고가×차이)을 표로, 차이 있는 것 위로. 줄 단위로 **"조정 제외"** 체크 가능. 안 센 품목은 표에 "미실사"로만 보이고 **조정하지 않는다**(기본).
5. **확정**(관리자): 확인 창에 총 조정 품목 수·늘어나는 개수·줄어드는 개수 표시 → 확인. 차이가 양수면 입고, 음수면 출고(**FEFO로 유통기한 묶음에서 차감**) 기록, 메모 `실사 조정 (이름 · 3→5)`, 층은 그 층. 실사는 `done`이 되고 수정 불가.
6. **취소**(관리자): `open` 상태 실사를 버림(재고 변화 없음). 확정된 실사는 취소하지 않고, 조정 기록을 기존 방식으로 건별 되돌린다.

### 서버 경로 (모두 로그인 필요, 확정·취소는 관리자)
- `POST /count/start` · `GET /count/list` · `GET /count/get?id=` · `POST /count/line`(품목 하나 입력) · `POST /count/finish`(`excluded` 목록 포함) · `POST /count/cancel`
- 입력 검증: 수량은 0 이상 정수·상한(예: 100000), 닫힌/없는 실사는 거절, 박스 입력은 화면이 개수로 환산해 보내고 서버는 개수만 받는다.
- **중복 확정 방지**: 확정 시 상태를 `open → done`으로 먼저 원자적으로 바꾸고(바뀐 행이 없으면 거절) 그 뒤 조정 기록을 넣는다.

### 화면
재고현황 도구 줄에 `[재고 실사]` 버튼 → 실사 목록(진행 중/완료) 팝업 → 선택하면 실사 화면.
```
재고 실사 · 3층 실사 (11/26)           센 품목 12 / 40      [차이 검토]
[바코드 스캔 또는 품목 검색 ____________]
 거즈 4x4      실제 [박스▾] [ 3 ] → 150개      김OO 14:02
 주사기 3cc    실제 [개수▾] [ 12 ]            이OO 14:05
 아직 안 센 품목 28개 ▾
```

### 새 모듈 `src/stocktake.js` (순수 함수, 테스트 대상)
- `adjustment(counted, sysAtCount)` → 차이(정수, 음수 가능)
- `buildReview(lines, products)` → 표 행(차이·금액·미실사 구분·정렬)
- `summarize(lines, excluded)` → 늘어나는/줄어드는/조정 품목 수
- 입력 정리 `normCountQty(v)`

## 제가 정한 것 (틀리면 고쳐 주세요)
- 실사 단위는 **층(+약품/물품)**. 한 번에 건물 전체가 아니라 층별로 나눠 센다.
- **직원도 셀 수 있고, 확정·취소만 관리자.** 사용자가 말한 "관리자 외 직원이 스캔으로 입출고" 사용 방식에 맞췄다.
- **기본은 블라인드**(전산 수량 숨김).
- 안 센 품목은 **그대로 둔다.** (전부 0으로 만들고 싶으면 기존 [재고 초기화] 사용)
- 로트(유통기한)별 입력은 하지 않고, 줄어드는 조정은 FEFO로 자동 차감한다.

## 구현자에게 맡기는 것
- 새 표 `CREATE`/인덱스 위치(기존 마이그레이션 목록에 추가), 경로 이름 세부, 화면 팝업 마크업·스타일
- 실사 중 품목 후보 검색을 기존 검색 함수로 재사용할지
- 확정 중 일부만 실패했을 때의 복구(현재 설계: 상태를 먼저 바꾸므로 실패하면 관리자에게 알리고 조정 기록을 수동 확인) — 더 안전한 방식이 있으면 제안

## 확인 방법
- 순수 함수·검증은 자동 테스트(RED→GREEN)
- 로컬 서버: 실사 시작 → 두 직원 계정으로 나눠 입력 → 센 뒤 입고가 생겨도 조정량이 센 시점 기준인지 → 확정 시 입출고 기록·FEFO → 두 번 확정 거절 → 열린 실사 취소 시 재고 불변
- 화면은 직접 눌러 확인(브라우저 자동 테스트 없음)
